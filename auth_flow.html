Spectra POC — Authentication & RBAC Flow

How a user signs in, gets a role from the database, and sees scoped data

User Action
Identity Provider
NextAuth
PostgreSQL DB
App (Browser)
Admin
1
User clicks "Sign In"
User chooses either Microsoft Entra ID or GovAuth on the home page.
2
Redirect to Identity Provider
NextAuth redirects the browser to the chosen provider's login page. The user enters their credentials there — we never see the password
3
Provider returns profile
After successful login, the provider redirects back to our app with the user's profile.
Provider sends: name email image
Provider does NOT send: role, agency, permissions
4
Prisma Adapter — Find or Create User
NextAuth's Prisma adapter checks the database: does a user with this email already exist?
Existing user? → Fetch their User row from DB
New user? → INSERT new User row + Account row into DB
5
createUser Event — Assign Default Role
Only runs for brand-new users (first login ever). Assigns the VIEWER role automatically.
UPDATE User SET roleId = (VIEWER role id)
This is why every new user starts as a VIEWER.
Note: This does NOT run on subsequent logins — only the very first time.
6
JWT Callback — Load Role & Agencies from DB
Runs on every sign-in. Queries the database for the user's current role and agency assignments, then embeds them in the JWT cookie.
SELECT User + Role + UserAgency + Agency

Writes into JWT cookie:
token.role = "VIEWER"
token.agencyCodes = ["GOVTECH", "MOH"]
token.agencyNames = ["Gov Technology Agency", "Ministry of Health"]
Key insight: After this step, role/agency data lives in the cookie. No database query needed on every page load — that's why we use JWT str
7
Session Callback — Expose to Components
Runs every time a component calls useSession(). Copies role and agencies from the JWT into the session object. No database query.
session.user = {
  id: "clx1abc...",
  name: "Justin Wang",
  email: "justin@tech.gov.sg",
  role: "VIEWER",
  agencyCodes: ["GOVTECH", "MOH"],
  agencyNames: ["Gov Technology Agency", "Ministry of Health"]
}
8
Dashboard Renders Based on Role & Agency
The app uses session data to control what the user sees.
ADMIN → sees ALL services, gets "Admin" link
EDITOR → sees their agencies' services, can modify settings
VIEWER → sees their agencies' services, read-only

Databricks query filtered by: WHERE service_name IN (services mapped to user's agencies)
Admin Changes a User's Role
A
Admin opens the Admin Page
An ADMIN user navigates to /admin. The admin layout checks their role — non-admins are redirected away.
B
Admin changes a user's role
The admin selects a user and changes their role from VIEWER to EDITOR.
PATCH /api/admin/users/[id]
Body: { roleId: "(EDITOR role id)" }

API route checks: is the requester an ADMIN?
→ YES: UPDATE User SET roleId = (EDITOR role id)
→ NO: return 403 Forbidden
C
Change saved in database
The user's role is updated in PostgreSQL immediately.
Important: The affected user's JWT cookie still has the OLD role. They keep their old permissions until they sign out and sign back in. On next sign-in, Step 6 (JWT Callback) re-reads the database and picks up the new EDITOR role.
